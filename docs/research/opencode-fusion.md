**What it is, in one line:** a config-only OpenCode setup (no framework, no build step) that splits work into a strong **main agent** that plans and reviews but is *mechanically unable* to edit files, and a cheap **sidekick** subagent that does all the editing — the "Devin Fusion sidekick pattern", applied through OpenCode's permission layer. It is a hand-rolled team configuration, not an orchestration framework.

## (a) Core orchestration primitive

The orchestrator is **explicit task delegation bounded by a permission graph**, not a loop, graph, or event bus. There is no orchestration code at all — the coordination mechanism is OpenCode's native `task` tool (subagent delegation) plus frontmatter permission rules that make delegation the *only* path to disk.

- Roles are defined as markdown files in the global config `~/.config/opencode/agent/*.md`. Each file's YAML frontmatter carries `mode` (primary vs subagent) and `permission`; the body is the prompt. `opencode.json` assigns only a model per role (`agent.<role>.model`). So it is fully **config-driven**, in OpenCode's own declarative schema — no plugin code enforces the core flow.
- The main `build` agent (mode `primary`) has `edit`, `grep`, `glob`, and `list` **denied** (denied tools are removed from its schema entirely), bash deny-by-default with a small verification/git allowlist, and a `task` **allowlist** naming only its specialists. The `sidekick` (mode `subagent`) has `edit: allow` and broad bash. The `plan` agent is the same brain as build but non-executing (read-only + delegation to explore/research/reviewer, never sidekick).
- Control flow per task (from `build.md`): receive request → delegate exploration (`explore`/`sidekick`) → decide the plan (optionally send plan to `reviewer` or the Claude bridge) → delegate execution via `task` with a five-part Spec → executor applies and reports → main reviews the diff (`read` + `git diff`, and runs lint/tests itself) → on miss, an **escalation ladder**: (1) re-delegate with feedback, (2) dictate a verbatim patch to be applied, (3) revise the plan; report a blocker only for non-code failures → main commits/pushes (with per-command user approval).
- The authors are explicit about **"enforced vs. advised"**: the permission layer enforces capability (edit is gone, so a model that "won't delegate" results in visible inaction, never a silent bypass); the prompt layer only advises quality (spec precision, cost discipline, parallelization). Skills are advisory in every harness, so nothing load-bearing lives in a skill.
- `subagent_depth: 2` (global) permits the main → executor → read-only-helper chain; the `task` permission graph independently bounds which named agents each role may spawn. No mid-session model routing and no dynamic graph rewiring — model assignments are fixed at startup. (README states dynamic mid-session model swapping is an explicit non-goal; it needs Devin's closed product.)

## (b) Agent definition & delegation

- **Definition:** one markdown file per role in `~/.config/opencode/agent/`, loaded by OpenCode as agent definitions. Frontmatter = mode + permissions; body = system prompt. Models deliberately are *not* in the prompt files (frontmatter would override `opencode.json`); they live in config as `provider/model-id` per role. `explore` is OpenCode's built-in read-only subagent and has no prompt file.
- **Delegation is explicit and main-decided.** The build agent routes work via the `task` tool using in-prompt routing rules, each with positive + negative cases (e.g. sidekick for mechanical edits but *not* judgment-heavy work; design for UI; research for web/docs; reviewer for plan critique and diff audit; vision only when the main model lacks image input). Delegation is bounded by each role's `permission.task` allowlist (e.g. build may spawn sidekick/explore/research/design/reviewer/vision; sidekick may spawn only explore/research; the built-in `general` subagent is explicitly excluded).
- **Both directions can escalate:** sidekick/design/research return `STATUS: escalate` naming the role that fits when handed misrouted or judgment-heavy work ("a half-done task routed to the wrong agent is more expensive to unwind than a fast, clean handback"). Agents are **reactive** (spawned on demand by delegation); there are no proactive/autonomous background agents, and the roster cannot dynamically spawn new roles.
- **Human-in-the-loop** stays at the edges: the setup skill interviews the user per role, and `git commit`/`git push` require per-command user approval.

## (c) Context & shared-state passing

- **No shared message history across the delegation boundary.** "The sidekick shares none of your conversation context" — hence the **five-part Spec contract** (Objective, Files, Interfaces, Constraints, Verification) the build agent must hand every executor, and the executor's structured **REPORT FORMAT** (`STATUS` complete/partial/blocked/escalate, `CHANGES`, `VERIFIED` with real command output, `GAPS`). A vague spec produces a bad guess; a complete spec is one the executor can run without asking.
- **State is carried by files on disk and structured text**: the diff the main reviews (`git diff`), verbatim code in dictated patches, and self-contained "packets" (for the optional Claude bridge, which cannot inspect the workspace). No typed shared-state objects, no vector memory.
- **The transcript IS shared between primary agents**: switching from `build` to the optional escape-hatch `normal` primary lets the new agent read earlier turns as its own — noted as a caveat (build will "apologise" for a direct edit the escape hatch made).
- **Observability/ground truth**: OpenCode's session DB records every agent's actual tool calls (`opencode db path`); the optional `fusion-audit` plugin logs the delegation tree (subagent sessions keyed by `parentID`) and per-agent token/cost accounting. "Did it really delegate?" is checkable, not vibes.
- **Compaction**: optional `compaction: { prune: true }` drops stale tool outputs on compaction — explicitly recommended because delegation-heavy flows inflate main-agent context. Otherwise no summarization layer; the prompts just tell the main to "keep context lean" and paste only conclusions.

## (d) Roster philosophy

- **Fixed, named, role-based roster** — deliberate and documented: core `build`, `plan`, `sidekick`, `explore` + a-la-carte `research`, `design`, `reviewer`, `vision`. Identity is the named agent file, not a slash command or a config block. The roster is static; depth is capped (`subagent_depth: 2`) so the tree is exactly main → executor → read-only helper.
- **Specialists over generalists**: the generalist built-in `general` subagent is *excluded* from every task allowlist, and roles are purpose-split (a cheap executor vs. a strong planner vs. a read-only searcher). "Delegate the doing, keep the deciding" is the motto.
- **Per-role model routing is a headline feature, not an afterthought**: each role gets an independent model so the user can put a frontier model on judgment (build/reviewer) and a cheap fast model on execution (sidekick/explore). Cross-vendor mixes are encouraged deliberately: "Models from one family share blind spots; a reviewer from a different lineage catches what same-family review misses" — cross-vendor review is a free side effect of the roster. Bundled subscription profiles (`opencode-go`, `opencode-zen`, `opencode-zen-free`, `chatgpt`, `github-copilot`) preset the roster's models.

## (e) Skills & tools shipped

- **One shipped skill**: `fusion-setup` — a conversational installer that writes the global config and copies the role prompts. It is explicitly non-load-bearing (the pattern must work whether or not a model ever loads the skill).
- **Slash commands** (optional): `/fusion-setup` (launches/reconfigures setup) and `/fusion-status` (health check: live tool schema, config on disk, agent files, Claude bridge). Note: TGO's "no slash commands" goal would treat these as installer conveniences, not runtime steering.
- **Plugins** (optional, OpenCode 1.x only): `fusion-audit.js` (observability — delegation tree + per-agent token/cost logs) and `fusion-claude.js` (a stateless, read-only plan-review bridge to the official Claude Code CLI for Pro/Max subscribers; refuses callers other than build/plan; runs in a neutral temp dir, no OAuth exposure).
- **Tools each role is granted via permissions**: `task` (delegation), `read`/`edit`/`bash` (selectively), `grep`/`glob`/`list` (only on executors), `websearch` + `webfetch` (research), the `skill` tool (design loads whatever design skills the environment has — "skills-over-MCPs" flavor), and the custom `fusion_claude_*` tools.
- **Notably: no MCP servers at all.** Providers are wired via AI-SDK adapters (`@ai-sdk/openai-compatible`, `@ai-sdk/anthropic`, etc.), and the one external integration (Grok via `progrok`) is a local OpenAI-compatible endpoint, not an MCP server. The human loops are OpenCode-native: `ask` permission mode and per-command approval.

## (f) Steal-worthy bits

1. **Permission-layer enforcement as the orchestrator** — delegate-by-construction: strip the main agent's `edit`/`grep`/`glob`/`list` and allowlist its `task` targets, so delegation is the only path to disk and a "won't delegate" model yields visible inaction, not a silent bypass. TGO's autonomy-without-slash-commands claim needs exactly this: capabilities, not compliance, decide which agent can act.
2. **Five-part Spec contract + structured REPORT FORMAT** for context-isolated subagents (Objective/Files/Interfaces/Constraints/Verification → STATUS/CHANGES/VERIFIED/GAPS). TGO's cheap executors and auditability fall out of it, and the fixed report fields double as a concise-writing constraint on subagents.
3. **The escalation ladder** — first miss re-delegate with feedback; second miss dictate a verbatim patch (turns the executor into "a pair of hands"); then revise the plan; plus reverse-escalation (`STATUS: escalate` to a named role) so misrouted work bounces fast. TGO gets bounded autonomy: work terminates, and no task deadlocks or gets half-done by the wrong agent.
4. **Named fixed roster with per-role model routing** — role identity via named agent files (not slash commands), each role on an independently chosen model, cross-vendor mix for free independent review. TGO's "named roster" ambition maps directly; the specialists-over-generalist and "delegate the doing, keep the deciding" split are the roster's operating rule.

Runner-up worth naming: **"skills are advisory, nothing load-bearing lives in one"** (the setup skill is just an installer) — validates TGO's skills-over-MCPs bias and warns against putting orchestration guarantees in skill files.
