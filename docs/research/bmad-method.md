Note: BMad is a **process/skills methodology, not a runtime**. It has no execution engine of its own; it installs a set of `SKILL.md` files into an IDE coding agent, and the host agent follows them. Coordination happens through durable documents and step-file instructions, not a supervisor loop or graph. This is a good contrast primitive for TGO (an actual orchestrator plugin).

## (a) Core orchestration primitive

A **right-sized, document-producing pipeline with an explicit routing state machine**, converging on one canonical implementation workflow.

- **Four phases**, each producing documents the next phase consumes: (1) Analysis (optional: brainstorm, forge-idea, deep-recon, product-brief, prfaq), (2) Planning (prd, ux, spec), (3) Solutioning (architecture, epics/stories, sprint-planning gate), (4) Implementation (build, code-review, correct-course, retrospective). "Small changes go straight to build; complex work gets the depth it needs." You may enter at any phase.
- **The routing/guidance primitive is `bmad-help`**: it scans project artifacts, detects which phase you're in, and recommends next steps in priority order — the method's substitute for a hard-coded state machine. Control flow between phases is carried by artifacts on disk, not code.
- **`bmad-build` is the convergence point**: a step-file workflow (`step-01-clarify-and-route` → `step-02-plan` → `step-03-implement` → `step-04-review` → `step-05-present`, or `step-oneshot`). It (1) compresses intent into one coherent goal with the human, (2) routes to the smallest safe path — one-shot (zero blast radius) vs plan-code-review, (3) runs longer with less supervision against the approved spec, (4) diagnoses failure at the layer it entered (intent vs spec vs local code), (5) brings the human back only at high-value checkpoints (intent interview, spec approval, final review). **Context-free subagents are "a cornerstone" of the review design**.
- **`bmad-build-auto`** is the unattended surface: one iteration of the same model, writing a machine-readable terminal status to the spec — `draft / ready-for-dev / in-progress / in-review / done / blocked` — plus `deferred[]` findings and `blocked` blocking-conditions, so an *external orchestrator* can drive it without parsing chat. It explicitly leaves "backlog policy" to the orchestrator.
- **`bmad-party-mode`** is the deliberation primitive: multi-agent discussion with an independence ladder (`session` = one model voices all → `auto` → `subagent` = one spawned agent per persona → `agent-team` = persistent peer team), falling back downward as the harness allows.

## (b) Agent definition & delegation

- **Every capability is a skill** — a `SKILL.md` directory the installer generates per agent, workflow, task, and tool. A generated skill's body just instructs the host to run `render_skill.py` and follow the printed `workflow.md`, which is a chain of step files. **A named agent is a skill that wraps a menu of related skills** with persona continuity.
- **Agent activation is a fixed 8-step sequence** (from `bmad-agent-dev/SKILL.md`): resolve customization (Python `resolve_customization.py`, merges shipped → team → user TOML) → run prepend steps → adopt persona → load persistent facts (`file:` entries load project docs) → load config (user name, language, artifact paths) → greet (with emoji icon prefix) → append steps → **dispatch or present menu**. If the user's opening message clearly maps to a menu item ("hey Amelia, let's implement the next story") the agent *skips the menu and dispatches directly*; otherwise it renders a menu of short codes (`BD`, `PRD`, `CA`…).
- **Who decides which agent acts next**: the *user* picks the top-level skill or agent (natural language), then the *workflow itself* routes autonomously (e.g. step-01 picks one-shot vs plan-code-review on blast radius; a skill's first step detects whether the incoming message names a spec and resumes at the matching stage). Within a workflow, subagents are spawned deterministically with a reference file as their entire prompt — context-free by design. Roster consumers (party-mode, retrospective, advanced-elicitation) pick participants from agent descriptors in central config.

## (c) Context & shared-state passing

- **Durable documents on disk are the state bus.** Two root folders from install config: `planning_artifacts` (briefs, PRD, SPEC, UX, ARCHITECTURE-SPINE, epics, stories) and `implementation_artifacts` (specs, `sprint-status.yaml`, cached `epic-<N>-context.md`, deferred-work). "Each document becomes context for the next phase… without this structure, agents make inconsistent decisions."
- **The spec is the canonical machine contract, with a single writer.** `bmad-spec` produces a five-field kernel (Why, Capabilities, Constraints, Non-goals, Success signal) + optional companions + optional `stories.yaml`, derived on every run from `.memlog.md`, an **append-only** decision log. Re-deriving from the log (never hand-editing the artifact) is what lets PRD/UX/architecture/epics feed the same spec "without merge drift." Spec frontmatter `status` is the machine-readable orchestration state.
- **Project context = kernel + bundle.** `kernel.md` is one small always-loaded file under an ~150–200 instruction budget, every line passing the pruning test ("would removing this line change agent behavior?"); the bundle is verified entries (`verified` vs `generated` trust frontmatter) loaded on demand via `index.md`, never wholesale. Placement modes: inject via BMad arrays, managed `AGENTS.md` blocks, or both — so the skill works standalone in any repo. A `context.py` script does all mechanical work (indexing, staleness, repo maps).
- **Sprint status** (`sprint-status.yaml`) is the single tracking artifact the whole cycle reads/writes; parsing, key derivation, and merging are done by a deterministic `sprint_plan.py` (never-downgrade merge), with the LLM only reconciling flagged edge cases.
- **Subagents are context-free** — each gets only its reference file as prompt, "so no single mind colors them all," and digests are written to disk as they land (a run that dies resumes from disk).

## (d) Roster philosophy

- **Five named agents, one per phase** (from `module.yaml`): Mary (Business Analyst, Analysis), John (PM, Planning), Sally (UX Designer, Planning), Winston (System Architect, Solutioning), Amelia (Senior Engineer, Implementation). Paige (Technical Writer) is on hiatus. Each has a short "essence" description (e.g. Amelia: "Test-first discipline… speaks like a terminal prompt: exact file paths, AC IDs…") used by roster consumers.
- **Hardcoded identity + customizable layer**: name/title/domain are immutable (you cannot rename Mary — "brand recognition survives customization"), while role, principles, communication style, icon, and menu are overridable via `_bmad/custom/*.toml` (team) and `.user.toml` (personal), merged at activation.
- **The stated philosophy: named agents beat menus and blank prompts.** Menus force the user to remember which capability lives on which agent; blank prompts make the user responsible for prompt engineering. "You say what you want, to whom, in whatever words feel natural." The menu remains as a fallback only.
- **Roster = lightweight descriptors in central config** (`[agents.*]`), so third-party consumers (party-mode, retrospective) can see and embody agents without touching skill folders; users can add fictional agents (Spock, McCoy) as pure descriptors. Party-mode's whole premise is that distinct personas holding different priorities (Architect guards design, PM guards scope, Dev guards buildability) surface tradeoffs in conversation.
- **Deliberately small**: the roster is five humans worth of perspective, not a swarm. Quality comes from right-sized process and context, not agent count.

## (e) Skills & tools shipped

- **Core module (always installed)**: `bmad-help`, `bmad-advanced-elicitation` (Socratic/first-principles/pre-mortem/red-team refinement), `bmad-review` (five lenses: adversarial, edge-case, verification-gap, structure, prose; one findings array; lenses run in parallel subagents), `bmad-customize`. Plus **thinking skills**: `bmad-brainstorming` (coach, 100+ ideas, anti-bias domain shifts), `bmad-deep-recon` (research in three modes — draft a prompt for your own deep-research tool, process a report, or run in-place with parallel fan-out + claim verification; six typed packs), `bmad-forge-idea` (one-question-at-a-time adversarial pressure test), `bmad-party-mode`.
- **BMM module (the agile suite)**: `bmad-product-brief`, `bmad-prfaq`, `bmad-prd`, `bmad-ux`, `bmad-spec`, `bmad-architecture`, `bmad-create-epics-and-stories`, `bmad-sprint-planning`, `bmad-build`, `bmad-build-auto`, `bmad-code-review`, `bmad-correct-course`, `bmad-retrospective`, `bmad-checkpoint-preview`, `bmad-project-context`.
- **Official modules**: BMad Builder (agent/workflow/module builder — the meta-module), Creative Intelligence Suite, Game Dev Studio, Test Architect (TEA). Web bundles package workflows as Gemini Gems / Custom GPTs.
- **MCP is optional, added via TOML, not required**: e.g. a team commits `persistent_facts` telling Amelia to always use the context7 MCP for library docs and fall back to Linear for story lookup; workflows expose `external_sources`, `external_handoffs`, `doc_standards` hooks. The default posture is skills + deterministic stdlib Python scripts (`memlog.py`, `context.py`, `resolve_*.py`, `render_skill.py`, `sprint_plan.py`) for everything mechanical.

## (f) Steal-worthy bits

1. **Named agents dispatched by natural language, menu as fallback** ("hey Amelia, implement the next story" skips the menu) — a direct, proven implementation of TGO's no-slash-commands + named-roster goals: the user talks to a teammate, the agent routes itself, and persona continuity (name/icon/voice) is a UX layer over plain skills, not new machinery.
2. **The single-writer, memlog-derived spec contract** — an append-only decision log from which the `SPEC.md` kernel is re-rendered on every run, with frontmatter `status` as the machine-readable state (`draft→ready-for-dev→in-progress→in-review→done/blocked`). That is exactly the anti-spec-drift, agentic-autonomy backbone TGO needs: autonomous workers can resume/route on status without chat parsing, and re-derivation makes concurrent planning workflows conflict-free.
3. **Compress-intent → route to smallest safe path, review-as-triage** — `bmad-build`'s one-shot vs plan-code-review routing, context-free subagent review, deferred (non-blocking) findings, and failure-diagnosis-by-layer give TGO a tested template for "run autonomously, but only as far as the work can safely go unattended," with review findings machine-readable (`deferred[]`, `blocked` condition codes) for the orchestrator.
4. **Deterministic stdlib-Python scripts for mechanical steps + a tiny verified context kernel** — parsing, indexing, state merging, and context curation are scripts (skills, not MCP clients), and project context is a ~150–200 instruction always-loaded kernel plus verified on-demand entries under a strict pruning test. Both are token-efficiency plays that directly serve TGO's skills-over-MCPs and concise-writing goals, and the kernel's "would removing this line change agent behavior?" test is a ready-made editing rule.
